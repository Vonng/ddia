事故档案：MongoDB 旧主库"复活"导致数据回退

真实事故叙事，记忆钩子

背景（2016 年前后，MongoDB 社区多起类似报告）

副本集中主库 M1 因网络分区被集群判死，选举 M2 为新主库。

分区恢复后 M1 重新上线，它仍带着自己未同步给 M2 的若干写入。

事故经过
  1. 分区期间，应用持续向 M2 写入，一切正常。
  2. 分区恢复，M1 以旧主库身份重新入群。
  3. 早期版本的 MongoDB 在主从切换（rollbacks）处理上不完善：

M1 上未被复制出去的写入被回退（甚至有报告称出现数据回退到旧状态）。

  1. 应用层没有幂等保护，部分在分区期间的"成功"写入实际上丢失，

且无任何报错——数据就是静默地变回了旧值。

根因
  • 异步复制下，旧主库崩溃前未复制的写入天然处于"不确定区"。
  • 修复机制（把旧主库未同步写入回退到文件）在早期版本中

可能造成应用可见的数据回退，而非仅回退到一致快照。

如果当时你负责，怎么避免？
  1. 幂等键：所有关键写入带唯一请求 ID，重试安全。
  2. 写确认策略：关键集合用 w:majority，宁可牺牲写入可用性。
  3. 升级版本 + 开启回退文件监控：即便用旧版本，也要监控

rollback 目录并在回退发生时告警、人工合并。

与权衡卡的连接

这正是 P-5.1-02（同步复制到几个副本？）和 S-5.1-01（主库崩溃推演）

的真实版本：半同步/多数派确认不是理论洁癖，是为了把

"静默丢数据"变成"显式失败"。

事故档案：Riak 集群"幽灵 resurrect"，被删除的数据回来了

真实事故叙事，记忆钩子

背景

Riak（Dynamo 风格无主复制）的一个生产集群。某键被用户明确删除，

删除操作以 tombstone（墓碑）标记写入多个副本。

事故经过
  1. 删除时部分副本收到了 tombstone，另一些副本因节点临时不可达没有收到。
  2. 集群后期做了节点替换/读修复，从"还有旧值"的副本把旧值

重新传播给了其他副本。

  1. 结果：用户看到已删除的数据重新出现。且因为删除用的是

LWW 语义，tombstone 与复活值之间的"最后写入者"判定

在时钟偏移下可能判错。

  1. 类似问题在多个 Dynamo 风格系统中反复出现（Riak、Cassandra

的墓碑与 GC grace 机制都是为此设计的补丁）。

根因
  • 无主复制中"删除"不是一个能靠多数派一次写就全局生效的操作，

它依赖墓碑在足够长的时间窗口（GC grace）内传播到所有副本。

  • 任何在此窗口外的副本复活（长时间宕机后回归、备份恢复），

都可能把旧值当作"新值"重新扩散。

如果当时你负责，怎么避免？
  1. 理解所用系统的墓碑/GC grace 配置，确保 grace 期大于

最长预期节点离线时间。

  1. 对"必须真的消失"的数据（合规删除），不依赖应用层删除——

用离线压实或专门的合规工具。

  1. 节点长期离线后回归时，不要直接信任其本地数据，

走全量重建。

这是 P-5.4-01（法定人数）揭示部分"反熵是异步的"的极端后果：

w + r > n 在墓碑没传播完的窗口内完全失效。

事故档案：MySQL RR 下的丢失更新导致库存超卖

真实事故叙事，记忆钩子

背景

电商系统，MySQL InnoDB，默认隔离级别 REPEATABLE READ。

库存表一行记录商品剩余数量，秒杀流程：

-- 事务 A 与事务 B 并发执行，均为 RR 级别
SELECT stock FROM items WHERE id = 1;   -- 两个事务都读到 1
-- 应用层判断 stock > 0，允许下单
UPDATE items SET stock = stock - 1 WHERE id = 1;  -- 各扣 1
事故经过
  1. 剩余库存 1，两名用户同时下单。
  2. 事务 A 和 B 的 SELECT 都读到 stock=1（各自快照），

应用层判断都通过。

  1. 两个 UPDATE 都执行成功（UPDATE 是当前读，各自把 1 改成 0——

实际上后提交的把先提交的结果覆盖）。

  1. 最终：卖出 2 件，库存只减了 1。一件不存在商品的订单生效了。
根因
  • 开发者以为"RR 隔离级别 = 事务安全"，实际上 RR（快照隔离）

不防止丢失更新：两个事务基于同一个快照做"读-改-写"，

后写的覆盖先写的。

  • UPDATE 语句用的是当前读，两个 UPDATE 都成功——

数据库层面没有违反 RR 的承诺，违反的是**业务不变量

（库存不为负）**，而它从未被数据库表达出来。

如果当时你负责，怎么避免？
  1. 原子更新：`UPDATE items SET stock = stock - 1

WHERE id = 1 AND stock > 0`，检查影响行数。最简单可靠。

  1. 显式锁：事务开头 SELECT ... FOR UPDATE，

让第二个事务等待。

  1. 乐观锁：UPDATE ... WHERE id = 1 AND stock = 1（带上读到的版本），

失败则重试。

  1. 结构性思考：这个 bug 属于"丢失更新"异常，

本质是应用层拿着快照数据做了决策。

与权衡卡的连接

这是 P-7.2-01（隔离级别选型）中"秒杀扣库存"陷阱的真实版本：

快照隔离的安全感是错觉，它保证你读到的历史一致，

不保证你基于它做的决策不冲突。

单节点够用吗？还是必须上分布式

先自己想方案，再揭示代价

新业务，预估 3 年数据量 200GB，峰值 QPS 2000，团队 4 人。

架构评审有人主张"一步到位上分布式"：分片、多副本、消息队列全上齐。

停下来，先想你的答案

现在该上分布式吗？判断依据是什么？上了会付出什么代价？

图

单节点与分布式的权衡：

flowchart LR
    S["单节点
一台机器扛全部"] --> S1["优点：无网络分区问题
事务简单、运维轻"]
    S --> S2["上限：受单机磁盘/内存/CPU 限制
故障即全停"]
    D["分布式"] --> D1["优点：容量与吞吐可水平扩展

    D --> D2["代价：网络分区、时钟不一致
部分失效成为常态"]
揭示
  • 判断依据是"单节点上限"是否真的成为瓶颈，而不是"分布式更高级"。

200GB / 2000 QPS 远在单机（现代服务器能轻松装下、能扛上万 QPS）范围内，

此时上分布式买不到任何东西，只买到问题。

  • 分布式的代价不是"多一点运维"，是一整类新故障模式：

网络分区、部分失效、时钟不可信、跨节点一致性。

第 9 章整章都在讲"这些不确定性无法被消除"。

在不需要扩展时引入它们，是用确定的复杂度换不存在的收益。

  • 你可能没想到的：DDIA 第 1 章把"分布式 vs 单节点"直接列为一种架构权衡，

与"云服务 vs 自托管""分析型 vs 事务型"并列——

说明"要不要分布式"是一个有正确答案的技术判断，不是品味问题。

正解通常是：单节点能做到就用单节点（配合良好的备份与快速恢复），

规模真的压过来时再拆，而且要按负载类型（读/写/容量）分别判断拆什么。

  • 配套判断：可以先把无状态的 API 层横向扩，把存储留在单节点，

这样能扩展最常见的瓶颈（并发连接）而不引入分布式存储的一致性问题。

抢库存要线性一致吗？先分清哪些操作真的需要

先自己想方案，再揭示代价

电商系统分布式集群，这些操作哪些要求线性一致（看起来像只有一份数据）？

① 秒杀扣减库存（不能超卖）

② 用户改自己的昵称后立刻刷新页面要看到新昵称

③ 朋友圈点赞数展示

④ 分布式锁的获取与释放

停下来，先想你的答案

逐一判断：哪些必须线性一致？哪些可以放宽？放宽的收益是什么？

图

一致性需求分层：

flowchart TB
    OPS["四类操作"] --> MUST["必须线性一致
① 扣库存（约束）
④ 锁（正确性依赖）"]
    OPS --> RYW["读己之写够用
② 昵称"]
    OPS --> FINAL["最终一致即可
③ 点赞数"]
    FINAL --> GAIN["放宽的收益：可用性↑
延迟↓，分区时仍可读写"]
揭示
  • 判断标准：操作结果是否参与"正确性约束"或被其他正确性依赖。

扣库存违反就是资损（超卖）；锁不线性一致等于没锁。

而昵称只要"自己看得到自己改的"（读己之写），

点赞数偏差几个根本无人在意（最终一致）。

  • 放宽的收益真实且巨大：线性一致要求读写都经过最新的数据副本，

主节点挂了要等切换（不可用）；最终一致在分区时各副本仍可独立读写。

CAP 定理说的就是这个：网络分区时，线性一致与可用性二选一。

  • 你可能没想到的：大部分系统 99% 的读不天然需要线性一致，

真正需要的是少数关键路径。把一致性当成本来付费，只为必要操作付费，

是分布式系统设计的第一堂经济学。

两个节点都说自己是主：脑裂怎么办？

先自己想方案，再揭示代价

主从复制集群。网络分区：主 M1 与多数派失联，但还能响应部分客户端。

监控判定 M1 超时，选举出 M2。短暂窗口内 M1 和 M2 都在接受写入。

停下来，先想你的答案

这个窗口的写入会有什么后果？共识协议（如 Raft）靠什么杜绝它？

图

脑裂窗口与共识的防护：

flowchart TB
    P["网络分区"] --> W["M1、M2 同时接受写
（脑裂窗口）"]
    W --> R1["普通主从：两边都持久化
分区恢复后丢一边或冲突"]
    W --> R2["共识协议：多数派投票
M1 无多数派 → 写入不被承认"]
    R2 --> F["恢复后全局唯一主 + 统一日志"]
揭示
  • 普通主从的窗口不是 bug 而是设计空白：M1 不知道自己已被罢免

（它的"失联"可能只是监控侧的误判），继续接受写入。

分区恢复后，两份互相矛盾的"真相"必须丢一边。

  • 共识协议的两道锁（你可能没想到的第二道）：

① 任期 + 多数派：M2 需要 2/3 节点投票才能上任，M1 拿不到多数派，

它的写入永远无法被提交（commit 需要多数派确认）；

② 更高的任期号：分区恢复后 M1 看到比自己新的任期号，立刻退位。

注意：即使 M1 暂时还没收到新任期消息，它的写入也因缺多数派确认而无效——

正确性不依赖"罢免消息及时送达"，这是与 fencing token 思想同源的防线。

  • 代价：共识要求多数派在线，2 节点集群容不了 1 节点故障

（2/2 投不出多数派）。所以共识集群用 3 或 5 个节点。

先自己想方案，再揭示代价

  1. 每步都要读写 HDFS，10 步 = 10 轮完整落盘
  2. 中间结果只是给下一步用，却要复制 3 份（HDFS 副本）
  3. 某步失败要重跑整步
停下来，先想你的答案

数据流引擎（Spark/Flink/Tez）做了什么改变来消除这些开销？

图

MapReduce vs 数据流引擎的执行模型：

flowchart LR
    subgraph MR["MapReduce"]
        M1["map→落盘"] --> M2["reduce→落盘"] --> M3["下一作业→再读"]
    end
    subgraph DF["数据流引擎"]
        D1["算子 DAG

代码里没有任何随机数。也没有 SQL 的 LIMIT 之类。

停下来，先想你的答案

不引入随机性，重跑结果为什么会不同？批处理的"确定性"边界在哪？

图

不确定来源的分类：

flowchart TB
    N["重跑结果不同"] --> R1["任务内部随机
(如抽样、UUID)"]
    N --> R2["读到外部可变状态

② 非幂等输出：结果表用 INSERT 追加而不是按分区覆盖，

执行，只有幂等 + 原子提交模拟出的效果等价。

    O["订单服务"] -->|REST + JSON

停下来，先想你的答案

扩容瞬间会发生什么？固定的分片数（如 1000 个逻辑分片）怎么解决这个问题？

图

你要为这三种业务各选哪个隔离级别？

先自己想方案，再揭示代价

同一个数据库实例上跑三种业务：

  1. 报表统计：凌晨跑一次全表聚合，算用户的总消费额
  2. 秒杀扣库存：高并发下 SELECT 剩余库存 然后 UPDATE 库存 - 1
  3. 余额查询页面：用户随时打开，看一眼自己的余额

约束：性能要尽可能好，不为不需要的保证付钱。

停下来，先想你的答案

三种业务各选哪个隔离级别：读未提交（RU）/ 读已提交（RC）/

可重复读（RR）/ 可串行化（S）？请先给三个答案和理由。

揭示
  • 报表统计 → RC（甚至 RR）：它读的是快照，不涉及并发写冲突，

关键是别读到"写了一半的事务"（脏读）。RU 省不了多少性能

还会看到未提交数据，没有任何理由选它。

这就是为什么 RU 在实践中几乎没人用——它唯一"优势"是省一点

读检查开销，代价是正确性。

  • 秒杀扣库存 → 看起来 RR 就够，其实是陷阱：RR 防止你两次

SELECT 读到不同库存，但**它不防止两个事务同时读到"剩 1 个"

然后都扣减成功**——卖超了。这是丢失更新（lost update），

需要 SELECT ... FOR UPDATE（显式加锁）或原子

UPDATE ... SET stock = stock - 1 WHERE stock > 0 绕过。

换 S 级别也能防，但高并发下代价大；工程主流是 RC/RR + 原子写。

  • 余额查询 → RC 足矣：单行读，RC 保证不读脏数据就够了。

值班医生系统：两个都撤销了自己的班

先自己想方案，再揭示代价

医院值班系统。规则：同一时段必须至少有一名医生在值班。

医生可以先查询自己是否值班，不是的话可提交"请假"事务。

现在：Alice 和 Bob 都在值班。两人几乎同时各自打开页面，

都看到"对方在值班"，于是都提交了请假事务。

两个事务都成功。时段内没有任何医生值班。

停下来，先想你的答案

这个场景在 RC 和 RR 隔离级别下分别会被阻止吗？

如果不被阻止，你用什么手段阻止？请先想，再看揭示。

揭示

RC 和 RR 都不会阻止它。这是写偏差（write skew）：

两个事务读了同一批数据（"谁在值班"），基于读到的结果写了

不同的行（Alice 请假、Bob 请假）。互不修改对方的行，

快照隔离（RR）管不到它。

为什么快照隔离挡不住？因为它承诺的是"每个事务的读来自一致快照"

——两个事务各自看快照都没问题，合起来却违反了业务不变量

（"至少一人值班"）。

可选的解法：

  • SELECT ... FOR UPDATE 显式锁定"值班中的所有医生"这些行，

强制两个事务串行化。最直接，但要求你知道该锁哪些行。

  • 物化冲突（materializing conflicts）：把"值班时段"本身

变成数据库里的行（时_slots 表），请假 = 更新该行，

冲突就落在同一行上了。丑但有效。

  • 可串行化隔离（SSI）：数据库检测到两个事务读了互相影响的数据

并发写，中止其中一个。代价是冲突率高时中止率也高。

图

写偏差：读同一批、写不同行：

flowchart TB
    A["Alice：查到两人值班"] --> WA["写：Alice 请假"]
    B["Bob：查到两人值班"] --> WB["写：Bob 请假"]
    WA --> R["两个事务都成功
时段的行各自被改"]
    WB --> R
    R --> BAD["业务不变量被破坏：
无人值班"]
记住这一句
写偏差 = "我读到的别改，我改的你别读"，快照隔离对它无能为力，这是升级到 SSI 的主要理由。

快照隔离（RR）能防止写偏差。

可串行化真的可以"免费"拿到吗？

先自己想方案，再揭示代价

你的团队在评审数据库选型。有人提议："直接全用可串行化（Serializable），

正确性问题一劳永逸，不用再操心各种异常。" 反对者说性能不可接受。

约束：系统读写混合，冲突集中在 10% 的热点账户上，其余 90% 数据

几乎无并发冲突。

停下来，先想你的答案

"全用 Serializable"的真实代价是什么？有没有办法只在对的地方付这个代价？

揭示

可串行化的三种实现，代价结构完全不同——这是选型的真正依据：

  • 两阶段锁定（2PL，传统 S lock）：读也加锁、写也加锁。

代价是所有并发被压低：读会阻塞写、写会阻塞读，

90% 无冲突的数据也被殃及，还可能死锁需要重试。

"全用 S"在 2PL 下确实很贵。

  • 串行执行（单线程，如 VoltDB）：所有事务排队执行。

极快的前提是每个事务很短、数据能放进内存。

一个慢查询就拖垮整个系统吞吐。适合特定架构，不是通用答案。

  • SSI（可串行化快照隔离，PostgreSQL/CockroachDB 的选择）：

乐观策略——先放行，提交时检测读写冲突再中止。

无冲突的事务（你的 90%）几乎零开销，

冲突集中处中止率升高、需要应用层重试。

所以反对者对了一半：2PL 时代"全 S"确实贵；

SSI 时代"全 S"对低冲突负载是可负担的——但必须配套重试逻辑，

应用要习惯"事务可能被中止，请再来一次"。

图

三种实现的代价落点：

flowchart TB
    S["可串行化"] --> P2["2PL（悲观）"]
    S --> SE["串行执行"]
    S --> SSI["SSI（乐观）"]
    P2 --> P2c["代价：所有并发被压低
读写互阻，死锁重试
90% 无冲突数据被殃及"]
    SE --> SEc["代价：一个慢事务拖垮全局
前提：短事务 + 内存数据"]
    SSI --> SSIc["代价：只惩罚真冲突
但应用必须处理中止重试"]
记住这一句
可串行化的代价取决于它的实现：2PL 压低一切并发，单线程要求短事务，SSI 只惩罚真冲突但要求应用会重试。

SSI 的主要代价是什么？
SSI 下无冲突的事务几乎零额外开销。

先自己想方案，再揭示代价

跨两个数据库的订单+库存扣减，用 2PC 保证原子提交。

流程：协调者问所有参与者"能提交吗"→ 参与者答"能"→ 协调者发"提交"。

参与者答"能"之后、协调者发"提交"之前，协调者进程崩溃。

停下来，先想你的答案

此刻参与者处于什么状态？它能单方面提交或回滚吗？为什么 2PC 被叫作"阻塞协议"？

图

2PC 的致命等待：

sequenceDiagram
    participant C as 协调者
    participant P1 as 库DB
    participant P2 as 库存DB
    C->>P1: prepare? 
    C->>P2: prepare?

  • 出路是共识：把"要不要提交"交给共识协议裁决（Raft/Paxos 化的协调者，

或直接用 Percolator/TiDB 这类基于共识的事务模型）。

这正是第 8 章通向第 10 章的桥：原子提交问题的正解就是共识。

停下来，先想你的答案

单机编程的哪些默认假设在分布式里失效？为什么不能"把网络做成可靠"来挽救？

推演：Lamport 时钟怎么给并发事件排序

逐步推演系统行为，先预测再看答案

推演序列

系统：两个节点 A、B，各自维护计数器（Lamport 时钟），规则：

本地事件计数器 +1；发消息携带计数器；收消息取 max(本地, 消息) + 1。

步骤 1：A 本地事件 a1。A 的时钟？

步骤 2：A 发消息 m1 给 B（时钟随行）。A、B 时钟各多少？

步骤 3：B 同时（并发地）做本地事件 b1，然后收到 m1。B 的时钟？

步骤 4：全系统需要给事件排序，b1 和 a1 谁先？这个"先"是什么意义上的先？

揭示

步骤 1：a1 → A = 1。

步骤 2：m1 携带 A=1 到达。A 发送后 = 2（按实现，发消息也 +1）。

步骤 3：b1 是 B 的本地事件，B = 1。收到 m1：

max(B本地=1, 消息携带=1) + 1 = 2。

步骤 4：Lamport 时钟保证：若 a → b（a 因果上先于 b），则 C(a) < C(b)。

但 b1 和 a1 是并发事件（互相不知道），时钟值相同并不区分先后——

算法用打破平局规则（如节点 ID 排序）给它们一个确定的全序。

关键认知：**这个"先"是人为约定的全序，不对应真实物理时间，

但只要所有节点遵守同一规则，全序复制状态机就有了理论基础**——

这正是共识协议（如 Raft 的 log index）排序请求的思想雏形。

逐步推演系统行为，先预测再看答案

推演序列

系统：电商事件日志表 events（10TB，按天分区）与用户表 users（100GB），

要算"每个城市的订单总额"。用 MapReduce 实现。

步骤 1：这两张表怎么放入 mapper？大表小表待遇一样吗？

步骤 2：mapper 输出什么？key 是什么？

步骤 3：reducer 拿到数据前，中间发生了什么？

步骤 4：为什么说 shuffle 是 MapReduce 的性能命门？

揭示

步骤 1：不对称。users 只有 100GB，可以整体加载进每个 mapper 的

内存/本地（"广播哈希连接"）；events 10TB 按块分给各 mapper 流式处理。

如果两张表都大（TB 级），就要靠 shuffle 端连接（相同 key 的记录

被分到同一 reducer）——代价大得多。

步骤 2：mapper 读 events 记录，查本地 users 副本拿到 city，

输出 (city, amount)；或输出 (user_id, event) 交给下游连接。

步骤 3：shuffle：所有 mapper 的输出按 key（city/user_id）分区，

经网络重分布到对应 reducer。这一步要落盘、要排序、要跨网络传输——

是整个作业唯一强制全局同步的环节。

步骤 4：因为 shuffle 的代价由数据倾斜决定。

如果某个 city 占了 30% 的数据（北京、上海），

那一个 reducer 要处理 3TB，其他 reducer 早早完成——

木桶效应：作业时长由最慢的 reducer 决定。

解决靠加盐打散热点 key、两阶段聚合。这也是批处理与流处理

共同的核心难题：分布式的墙是数据倾斜，不是算力。

推演：流处理如何做到"恰好一次"效果

逐步推演系统行为，先预测再看答案

推演序列

系统：Kafka 消费者读事件 → 更新状态（累加计数）→ 写出结果。

消费者可能随时崩溃重启。

步骤 1：如果消费者每处理一条就提交 offset，崩溃后会丢吗？还会重复吗？

步骤 2：如果先处理、后批量提交 offset，崩溃后有什么后果？

步骤 3：既然无法避免重复投递，怎么让重复不影响最终结果？

步骤 4：把状态也存在内部（RocksDB）而不是外部数据库，又带来什么新问题？

揭示

步骤 1：可能丢。提交了 offset 但结果还没写完（或已写完但下游没收到），

重启后从新 offset 开始，那条数据永远不会被再处理。

→ "最多一次"（at-most-once），丢数据。

步骤 2：可能重复。处理完了但 offset 没提交，重启后重放，

同一条数据被算两遍。→ "至少一次"（at-least-once），数据正确性受损。

步骤 3：幂等 / 可重放两条路：

① 幂等写入：结果表以事件 ID 为主键 upsert，重复处理结果不变；

② 事务性写入：把 offset 提交与结果写入放进同一个原子事务

（Kafka 事务、或 Flink 的 two-phase commit sink），

要么都生效要么都不生效——**这就是"恰好一次"的全部秘密：它不是不重复投递，

而是让重复投递不可见**。

步骤 4：状态在内部意味着状态本身也要容错：

靠 checkpoint（定期把状态快照到持久存储）+

从 checkpoint 对应的 offset 重放输入日志来恢复。

所以"恰好一次"需要一个可重放的输入日志作为前提——

这就把流处理的容错和 12.1 的日志模型锁在了一起。

接下来发生什么？

步骤 3：此时查询 user:1。查找顺序是怎样的？最坏要查几处？

步骤 4：继续写入 user:1 = "大明"（同键新值）。

揭示

步骤 1：只写内存 memtable + 一条 WAL 日志（防崩溃丢数据）。

磁盘上的 SSTable 没有任何变化——写入是纯内存操作，所以快。

步骤 2：memtable 整体刷盘为一个新的 SSTable 文件（不可变），

这是 LSM 写吞吐高的根源。

所以 LSM 必须配布隆过滤器，否则空查询代价极高。

步骤 4：返回"大明"。靠"新层级优先 + 层内按时间排序"的规则：

memtable > L0 新文件 > L0 旧文件 > L1。旧值要等后台合并（compaction）

逐步推演系统行为，先预测再看答案

推演序列（每步先自己预测，再看下一步）

系统：主库 L，同步从库 S1，异步从库 S2。客户端发出写入 X = "转账 100 元"。

步骤 1：L 收到 X，写入本地日志，但尚未向任何从库转发。

→ 此时 X 存在于哪些机器？

步骤 2：L 把 X 发给 S1（同步），S1 写入并确认。

→ 此时 L 可以向客户端确认 X 了吗？

步骤 3：L 在向客户端发确认之前崩溃，同时 L 的磁盘损坏。

S2 还没收到 X。客户端没有收到"成功"，但也没有收到"失败"。

步骤 4：集群选举 S1 为新主库并恢复服务。

→ X 现在处于什么状态？客户端应该重试写入 X 吗？

揭示

步骤 1：只有 L。X 是"未确认"状态。

步骤 2：可以。S1 已持久化 X，L 崩溃后 X 仍可存活。

步骤 3：关键点——"不确定区"（ambiguous write）。

客户端超时后无法区分"提交了"和"没提交"。

X 在 S1 上存在，但旧主库已无法说明它是否被确认过。

步骤 4：S1 上有 X，新主库恢复后 X 会出现。

客户端重试 X 会导致重复转账（如果没有幂等键）；

不重试则可能丢失这笔转账（如果 S1 的日志也被判无效）。

两种选择都可能错，这正是分布式事务和幂等性在后续章节存在的理由。

记住这一句
客户端视角的"不确定"（超时无响应）和系统内部的复制状态互相纠缠，这是幂等写入被强制要求的最根本原因。

逐步推演系统行为，先预测再看答案

推演序列

系统：单主 L + 从库 A（滞后 200ms）+ 从库 B（滞后 5s，正在从网络抖动中恢复）。

时间轴 T=0 起，事件如下：

步骤 1：T=0，用户 U 把昵称从"小明"改为"大明"（写入 L，异步复制）。

L 立即向 U 确认成功。

步骤 2：T=100ms，U 的刷新请求被负载均衡到从库 A。

→ U 看到的昵称是？（A 的滞后 200ms，此时刻 L 的 T=0 写入尚未到达 A）

步骤 3：T=250ms，L 的写入到达 A。U 再次刷新，这次被路由到从库 B。

→ U 看到的昵称是？

步骤 4：T=2s，L 的写入仍未到达 B（网络抖动加剧）。

运营同事在后台把 U 的昵称又改回了"小明"（写入 L）。

U 的第三次刷新被路由到 A。

揭示

步骤 2：旧值"小明"。写入已确认但还没复制到 A——这就是

"主库确认 ≠ 全局可见"。

步骤 3：仍是"小明"，而且是从更新过的 A 跳回到落后的 B。

U 会感觉自己改的东西"变了回去"，比单纯看不到更新更让人困惑。

这就是单调读要解决的问题：同一个用户的连续读不应往回走。

步骤 4：A 上此刻是"大明"（第一次修改已到达），

而全局的最新值其实是"小明"（第二次修改，尚未到 A）。

U 看到了一个从未在全局存在过的状态序列：

小明 → 大明，实际上全局历史是 小明 → 大明 → 小明。

但 U 的体验是合理的，因为单调读只约束"不回退"，

不承诺看到最终状态。

推演：二级索引在分片集群里的两种命运

逐步推演系统行为，先预测再看答案

推演序列

系统：4 分片集群，表 orders(order_id 分片键, region, status)。

需求：按 region 查订单列表。两种二级索引方案：

  • 方案 A（本地索引）：每个分片只对自己那份数据建 region 索引
  • 方案 B（全局索引）：region 索引的数据本身按 region 值分片，覆盖所有分片的数据

步骤 1：方案 A 查 region = '华东'，请求怎么走？代价随什么增长？

步骤 2：方案 B 查同一条件，请求怎么走？

步骤 3：方案 B 写入一个订单（region='华东'），发生了什么？

步骤 4：选择方案。

揭示

步骤 1：请求散射到全部 4 个分片，各查各的索引再合并（scatter-gather）。

代价随分片数线性增长——分片越多，这种查询越慢，尾部延迟由最慢分片决定。

步骤 2：只读 region 索引所在的分片（'华东'只在一个索引分片上），

一次点查搞定，与总分片数无关。

步骤 3：写入要跨两个分片：订单本体写入分片键所在分片，

同时更新 region 索引分片。这两个写入无法用一个本地事务包裹

（跨分片分布式事务，见第 8 章的代价）——所以全局索引普遍是异步更新，

读索引可能看到稍旧的订单列表。

步骤 4：MongoDB 的选择：本地索引（查询必须 scattering）；

DynamoDB/Couchbase 的选择：全局二级索引（写入放大 + 最终一致）。

规律：二级索引让"读路径 shortest"和"写路径 single-shard"不可兼得。

四种隔离级别下，这笔并发读取各看到什么？

逐步推演系统行为，先预测再看答案

推演序列

初始状态：账户 A 余额 100，账户 B 余额 100。

两个事务并发执行：

  • T1（转账）：BEGIN → A 扣 10（A=90）→ ……尚在执行……
  • T2（统计）：BEGIN → 读 A → 读 B → COMMIT

时间轴：

T1 执行了"A 扣 10"但尚未提交；T2 此刻读 A 和 B。

逐级推演（先自己回答再看揭示）：

RU 下 T2 读到的 A、B 各是多少？

RC 下呢？RR 下呢？

追加时间轴：T1 继续执行 B 加 10（B=110），T1 提交。

假设 T2 是 RR 级别且在 T1 提交前就已开始，T2 此刻重读 A 和 B

（再算一次总额），读到多少？

揭示

RU：A=90，B=100。读到了未提交的扣减。

如果 T1 之后回滚，T2 看到过一笔从未发生的扣款——脏读。

总额 190，既不是转账前也不是转账后，哪个都不对。

RC：A=100，B=100。只读已提交数据，总额 200，一致。

但注意：T1 提交后 T2 若再读一次，会看到 A=90——

同一事务内两次读结果不同（不可重复读），RC 允许。

RR：A=100，B=100，且 T1 提交后重读仍是 100——

快照固定在事务开始时刻。总额恒为 200。

追加推演（RR 重读）：A=90，B=100——注意 B 还是 100！

T1 对 B 的写入发生在 T2 快照之后，T2 看不到。

这就是 MVCC 快照读的规则：整个事务只看"开始时刻的快照 +

自己写的"。总额算出 190？不——A=90、B=100，总额 190，

是一个全局从未存在过的状态（转账前是 200，转账后是 200）。

对报表场景这通常可接受（近似值），

对审计场景就是事故。

推演：进程暂停如何偷走你的锁

逐步推演系统行为，先预测再看答案

推演序列

系统：客户端 C1 获取分布式锁（租约 10s）操作存储节点 S，

锁保护"不能重复执行"的任务 X。

步骤 1：C1 拿到锁，开始执行。它需要检查"我还持有锁吗"吗？

步骤 2：C1 执行到一半，发生一次 15s 的 GC stop-the-world 暂停。

租约 10s 到期，锁服务把锁发给了 C2。C2 开始执行任务 X。

步骤 3：C1 从 GC 中醒来。它以为自己还持有锁（代码没检查），

继续写存储。现在几个客户端在执行任务 X？

步骤 4：怎么防？

揭示

步骤 1：不能用"查一下锁还在不在"来防——

查完、GC 暂停、再用，中间照样可能失去锁。

租约是个时间窗承诺，不是持续状态。

步骤 3：两个客户端同时执行任务 X。

这就是"进程暂停"的恐怖之处：从 C1 的视角，它只是执行了几行代码之间的间隙；

从全局看，15 秒过去了，世界已经变了。**GC 暂停、虚拟机挂起、

NTP 跳变都可能在任意两条指令之间插入任意长的暂停**——

单机编程里"这段代码是原子的"的直觉在分布式里全部失效。

步骤 4：栅栏令牌（fencing token）：锁服务每次发锁都发一个单调递增的编号。

C1 拿的是 33，C2 拿的是 34。存储节点记录见过的最大编号，

拒绝比它旧的（33 的写入被拒）。C1 醒来后继续写时自动被挡下——

它不需要"知道"自己失去了锁，编号替它说了实话。
